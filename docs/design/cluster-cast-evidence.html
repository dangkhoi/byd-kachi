Persistence boundary

  • AtomicFile is hidden behind AtomicBytes for JVM fault injection.
  • All reads and writes occur inside CastSessionStore.locked.
  • Checksum covers the complete deterministic payload; unknown schema and corrupt data never produce a baseline.
  • Transaction epoch cannot exceed or reduce the durable epoch.

Build boundary

  • collectAuthorizedApk is not an assemble finalizer.
  • Requires requested release variant, slice, and 64-char exact-source ID.
  • Accepts exactly one release APK created after this Gradle invocation.
  • Copies to a unique same-directory temporary file, then publishes by ATOMIC_MOVE (safe no-replace fallback) and always cleans the temporary path.
  • Writes ClusterNav-<version>-<slice>-<source12>-release.apk and refuses overwrite, including publication races.

Technology validation

Gradle · official current user guide

/websites/gradle_current_userguide returned current examples for tasks.register, abstract custom task types, @Input Property<String>, DirectoryProperty/RegularFileProperty, and Provider-based lazy configuration. The collector follows those patterns and preserves the existing Gradle 8.7 / AGP 8.5.2 / Kotlin 1.9.24 toolchain; no upgrade or dependency was authorized.

Android AtomicFile · official API

The first Context7 query against /websites/developer_android did not retrieve AtomicFile; it returned unrelated AppCompat and Java atomic entries. This is the recorded Context7 query limitation. Direct retrieval of the official developer.android.com/reference/android/util/AtomicFile page confirmed API 17, complete write + sync before rename, startWrite → finishWrite, failWrite on failure, readFully/openRead, and explicitly no file-locking semantics; the caller must provide mutual exclusion.

No new dependency: Stage 2 uses Android platform AtomicFile, Gradle managed task properties, and JDK/Kotlin standard APIs already available in the approved build.

Open issues

  • Stage 3 must provide vehicle-profile parsing and runtime integration without changing the Stage 2 gateway ownership boundary. Stage 2 now observes build fingerprint provenance and exposes validated parameterized package resolution; it does not claim vehicle-profile support.
  • AtomicFile has no locking semantics. Stage 2 requires one coordinator/store writer; process separation, if later approved, must retain a single Cast writer through typed IPC. Android process-kill and physical reboot evidence remain future-gated.
  • Envelope schema v1 is the first disabled V2 envelope. Before enablement, a future stage must implement the approved N/N−1 reader or explicit no-downgrade fence plus rollback-readable snapshot.
