[P1] Cluster-centre HUD keep-alive re-asserts the last maneuver every 400 ms with no max age, and the disconnect path never clears it

B1-hud-stale-frame-pinned-forevereffort Ssafetynav-domainarchitecture
Ảnh hưởng

In the DEFAULT configuration (Cast off ⇒ navOnlyMode ⇒ centre nav active), if the source dies without removing its notification — head-unit drops the listener binding mid-drive, GMaps frozen by the OEM task-killer with its ongoing notification retained — the OEM centre overlay keeps being rewritten every 400 ms with the last maneuver, e.g. 'rẽ phải · 200 m · Trần Hưng Đạo', past the junction and past the destination, with nothing to bound it. Before 1.15 the OEM's own ~1 s blank was the accidental safety valve; the keep-alive deliberately removed it. A frozen confident wrong arrow on an instrument cluster is worse than no arrow. Verifiers correctly narrowed this to a compound failure (rebind usually recovers in seconds) and it self-corrects on the next notification, which is why it is P1 and not P0 — but it is the only finding in the whole review that puts wrong guidance on a moving car's cluster with no time bound.

Bằng chứng

I re-read HudKeepAlivePolicy myself: it has exactly three fields (lock, lastWriteAtMs, hasFrame) and shouldReassert is hasFrame && nowMs - lastWriteAtMs >= intervalMs — there is no age ceiling anywhere in the class. onFrameWritten is called on real pushes AND on every keep-alive re-assert, so the 400 ms tick re-arms itself indefinitely. NavNotificationListener.onListenerDisconnected — whose own KDoc says the head unit does this 'lúc chạy' — clears typed sources and calls requestRebind but never NavRepository.stop, so hudOwner.stop() is never reached. The lane strip self-clears at 180 s via AmapEmissionArbiter STOP, but that STOP lands on HudMirrorController (a no-op recorder), never on the HAL owner. Two lanes found this independently and the nav-domain verifier returned CONFIRMED at P1 after failing to find any guard. Related second symptom from the architecture lane: NavigationHudOwner.start() has only two call sites (NavRepository:111 once per process, and setOutputEnabled(CLUSTER_LANE,true)), so after the first route's stop() the heartbeat is cancelled and never re-armed for route 2.

Cách sửa

In NavigationHudOwner, record lastRealPushAtMs in push() separately from lastWriteAtMs (a re-assert must NOT refresh it) and make the keep-alive stop re-asserting once now - lastRealPushAtMs > ~15-20 s, issuing BydHal.clearNavFrame once and calling keepAlive.onCleared(). Add NavRepository.stop(applicationContext) + ClusterNavLaneWidget.onNavIdle() to NavNotificationListener.onListenerDisconnected, mirroring the removal path at :223-228. Separately re-arm the heartbeat from the delivery path (the if (keepAliveTask == null) guard at :107 already makes start() idempotent) so route 2 in the same trip is protected. Add a HudKeepAlivePolicyTest case: after N intervals with no real push, shouldReassert must be false. Do NOT remove the heartbeat itself — the ~1 s OEM blank it was built to kill is a confirmed on-car symptom.

Phán quyết verify

CONFIRMED by the nav-domain verifier at P1 after an explicit refutation attempt; found independently by 3 lanes; I re-verified the missing max-age term in HudKeepAlivePolicy myself. Strong cross-lane agreement.

[P1] PiP is denied for Google Maps/YouTube system-wide with a RAM-only restore map; any non-graceful death — including the app's own OTA — makes it permanent with no undo anywhere

B2-pip-appops-deny-permanent-on-third-party-appseffort Ssafetyarchitectureux
Ảnh hưởng

A friend enables Cluster Cast once, then takes any OTA. Google Maps and YouTube lose picture-in-picture permanently on their head unit. The app-op belongs to those apps and persists in /data/system/appops.xml across reboot; uninstalling ClusterNav does not clear it. There is no ClusterNav UI to undo it, nothing tells them ClusterNav did it, and the only remedy is a manual appops command or a factory reset. This is the clearest 'do not do this to someone else's car' item in the review: an invisible, irreversible modification of third-party software on hardware you do not own. It is also a direct CLAUDE.md §5 violation — state changed outside the process with a restore path that dies with the process.

Bằng chứng

FloatingBubbleService:57 holds pipPreviousModes as a plain in-memory mutableMapOf, written on a raw 'pip-block' thread that issues appops set <pkg> PICTURE_IN_PICTURE deny for a hardcoded 5-package list (:495-501), and restored ONLY from onDestroy (:186). The re-arm guard at :370 is if (prev != null && prev != "deny"), so on the next start queryPipMode returns 'deny', nothing is recorded, and the map stays empty forever — even a later graceful stop restores nothing. The app's own updater guarantees the non-graceful kill: UpdateChecker:99 documents that a successful -r kills the process immediately. V1 knew this and persisted the marker BEFORE the write (ClusterCast.kt:124 '★ … LƯU BỀN để còn trả lại nếu app chết giữa chừng'); the simplified rewrite dropped it. There is a measured precedent in this repo: CastColdBootstrap.kt:150-183 records the identical residue on 2026-07-31 leaving vn.vietmap.live's PiP silently dead until a manual appops … allow, and CastPipResidueTest was written to lock that class of bug in V2 — with no equivalent for the simplified path.

Cách sửa

Persist the previous mode into simple_cast_prefs BEFORE issuing appops set … deny (key pip_prev_<pkg>) and restore from that store at FloatingBubbleService.onCreate before re-applying, exactly the pattern V1 used. Keep the RAM map only as a cache; replace mutableMapOf with ConcurrentHashMap and run block/restore on the coordinator's serial executor rather than two unsynchronised raw threads. Add the missing --user 0 for consistency with CastShell.kt:177. Strongly consider dropping the appops write entirely — SimpleCastCoordinator.foregroundPackage already calls dismissPipOnDisplay and CastStackParser.foreground already skips pinned stacks, so it is doubly redundant for its stated purpose. Also ship a one-shot cleanup that restores any package still recorded as blocked, so cars already carrying the residue heal on the next update.

Phán quyết verify

CONFIRMED by the safety verifier after a five-angle refutation attempt; found independently by 3 lanes; the repo contains its own measured field precedent for the identical failure.

[P1] Every failed OTA install reports success: dadb 2.0.0 RETURNS InstallResult instead of throwing, and the return value is discarded

B3-ota-install-failure-reported-as-successeffort Ssecuritybuild-release
Ảnh hưởng

A driver taps 'Tải & cài'. pm install -r refuses the APK — wrong signer (debug↔release) or insufficient storage on a storage-tight head unit. dadb returns Failure without throwing, so install() returns 'đã cài — đang mở lại…', UpdateRelaunch.cancel at :113 is skipped, and the armed alarm relaunches the SAME old build 5 s later. The driver believes the fix you told them to install has landed; it has not, and they keep driving on the unfixed binary. This is precisely the CLAUDE.md §9 failure — 'Không bao giờ đoán xe đang chạy bản nào' — and it makes every subsequent remote diagnosis unreliable, because the one signal that tells you an install did not happen is suppressed. The security framing is overstated (Android's signature verification is fully intact; nothing unauthorised installs), but the reporting defect is real and it is upstream of everything else you do remotely.

Bằng chứng

LocalDeviceShell.installApk is runCatching { Dadb.create(HOST,PORT,keys).use { it.install(apk,*options) }; true }.getOrDefault(false) — the InstallResult is a discarded expression and true is unconditional. The verifier went past the javap signature and decompiled the resolved jar: in Dadb$DefaultImpls.install BOTH failure paths construct and RETURN InstallResult$Failure (no athrow), so runCatching never fires. Critically, dadb 1.2.10 declared void install(File, String...) throws IOException — failure was thrown, and the runCatching { install(); true } idiom was CORRECT. The 2.0.0 bump inverted the contract silently, and because Kotlin does not flag a discarded return value the code kept compiling clean. UpdateChecker.kt:102-104 carries a KDoc asserting the exact opposite guarantee ('trả false khi dadb báo lỗi … trước đây hàm này BỎ QUA giá trị đó'), i.e. this bug was fixed once and reintroduced by the dependency upgrade. No test covers the false path.

Cách sửa

Capture the result and branch inside the existing runCatching: val r = adb.install(apk, *options); r.onFailure { return@runCatching false } — or wrap r.orThrow() so a Failure becomes false. Surface the Failure reason string up through UpdateChecker.install so the user and the log see why. Add app/src/test/.../UpdateCheckerTest cases faking a Failure and asserting install() returns the failure string AND that UpdateRelaunch.cancel ran. This is also the moment to add a verifyDependencyContract-style note: pin dadb and re-read its API on every bump.

Phán quyết verify

PARTIAL→P1 after verification. Mechanism fully reproduced by decompilation; the P0 security framing was correctly rejected (the platform's signer check still holds), but the misreporting defect stands and is a genuine silent dependency-upgrade regression.

[P1] VietMap widget host and a 900 ms privileged-shell logcat poller start ABOVE the master-switch gate and run forever with both switches off, feeding a no-op sink

B4-ingest-starts-above-master-switch-gateeffort Scritic
Ảnh hưởng

A friend grants notification access, leaves both master switches OFF believing the app is idle — which is exactly what docs/HUONG-DAN.md promises them ('mở app lên không tự đụng gì vào xe') — and from then until power-down ClusterNav opens roughly 4,000 authenticated ADB sessions per hour to localhost:5555, forks 4,000 uid-2000 shells running logcat, writes ~4,000 of its own logcat lines and posts a main-thread runnable every second, on an Android 10 head unit whose spare CPU and RAM are what the OEM launcher and CarPlay/AA need. Then gate startWazeHudSource additionally on WazeMod being installed and on Prefs.sourceMode ∈ {PREFER_WAZE, AUTO}, and gate bridge.start on Prefs.speedLimitSource == VIETMAP. Raise POLL_MS, or hold one long-lived dadb session for the poller rather than Dadb.create per command. Lock the gate ordering with an :app contract test in the NavCastUiWiringContractTest style — this is the one place those source-grep tests earn their keep.

[P1] The only precondition protecting CP/AA from the documented freeform crash can never fire — but the obvious fix would break CP/AA casting entirely

C1-cp-aa-fullscreen-guard-deadeffort Marchitecture
Ảnh hưởng

SimpleCastModels:220-222 states that on DiLink3 freeform windowing of CarPlay crashes surfaceflinger and leaves the cluster unrecoverable, requiring a power-cycle. If that is true, this guard is the thing that was supposed to stop it and it does nothing. BUT the crash consequence is NOT field-proven — the spec itself says 'source says can crash', there is no logcat or field record of an SF crash anywhere in docs/diagnostics, and CP casting was exercised repeatedly on the real car as recently as 2026-08-12 with the freeform placeholder resident, producing 'ClusterNav kẹt trên cụm', not an unrecoverable cluster. Per CLAUDE.md §2 the hazard sits at 'nhiều khả năng', not 'đã chứng minh'.

Bằng chứng

CastGeometryController requires displayId=$displayId AND windowingMode=5 on ONE line of am stack list. Across every diagnostic dump in the repo, windowingMode=5 occurs ZERO times — the real tokens are mWindowingMode=fullscreen (683), undefined (58), freeform (24), always on the configuration line FOLLOWING the Stack id=… displayId=N header. The project's own CastStackParser already models this multi-line carried-state format. So freeformOnly is always false and verifyFullscreenStackAvailable always returns true; it has exactly one call site and zero tests. The verifier found it is worse than filed: SimpleCastCoordinator launches ClusterBlackActivity with --windowingMode 5 on display 1 at EVERY projection open and CastStackParser deliberately KEEPS that placeholder through cleanup, so a freeform-only display 1 is the routine state, not an edge case. The approved spec required the opposite behaviour explicitly (clusternav-v102-review-remediation.html R4: fail-closed; 'never guess'), so this is a genuine scope gap.

Cách sửa

DO NOT apply the filed recommendation literally. Requiring a fullscreen+standard stack and failing closed would reject essentially every CP/AA cast, because the resident placeholder on display 1 is freeform by design — you would break a working shipped feature to close a speculative hazard. The correct fix is to make the CP/AA path FORCE a fullscreen destination: parse the header/configuration line pair the way CastStackParser already does, and either resolve-or-create a mWindowingMode=fullscreen mActivityType=standard stack on the cluster, or set the windowing mode after move-task. Lock it with a regression test over the verbatim fixture docs/diagnostics/carlog-2026-07-23-trace/live/02-am-stack-list.txt (CLAUDE.md §10). Run the on-car probe first (see probe list) so you know whether you are fixing a real crash or a paper one.

[P1] OTA is strictly one-way and the only rollback a friend has — uninstall and reinstall — destroys the ADB keypair every feature depends on

C2-no-rollback-and-reinstall-destroys-adb-keyeffort Mcritic
Ảnh hưởng

A friend's car takes an OTA that regresses their head unit — this repo's own history contains exactly that class of event (a build that froze the Dudu launcher; the 1.04 build you now blocklist). They have no way back: the updater cannot offer an older version and pm install -r refuses the downgrade. The natural user action — uninstall, reinstall the older APK — silently discards the keypair; the reinstalled app generates a fresh key the head unit's adbd has never authorised, and re-authorising needs an 'Allow USB debugging' dialog on a screen they may not get. Bằng chứng

UpdateChecker only ever moves forward: it selects the highest version in apk/ and offers it only when cmp(best, current) > 0, with no UI or API for an older version anywhere in the file, and installs with -r and no -d. Cách sửa

Minimum before the next OTA to a non-owner car (S): write the manual recovery procedure into README's install section and the user guide — adb connect over WiFi with CarPlay unplugged, then pm install -r -d <older apk> — plus what to expect if the key is lost. [P2] The 1.18 re-pin watchdog cannot tell 'an external trigger stole it' from 'the driver deliberately opened it', has no give-up condition, zero tests, and treats a failed shell read as proof the app escaped

C4-repin-watchdog-fights-the-drivereffort Mpo-releasearchitecturesafetyqa
Ảnh hưởng

Driver split-casts GMaps and taps GMaps on the centre screen to change destination; ~8 s later the watchdog relaunches it onto the cluster, and re-arms every ~10-14 s for as long as they keep pulling it forward. Verifiers correctly narrowed the severity: a single bubble tap dispatches Stop and shuts the loop off, the feature is behind the opt-in Cast master switch, only NORMAL apps are affected (CP/AA are excluded structurally), and nothing touches home/pinned stacks — so this is an attention sink, not the CLAUDE.md §4 launcher-orphan class. The unmeasured risk is PARTIAL shell failure (am stack list failing while am start succeeds), which would relaunch a correctly-placed navigating app every 10 s. The owner's own changelog still lists this under 'Cần test trên xe'.

Bằng chứng

Four lanes found this from four angles. doRepinEscapedCastApps keys ONLY on geometry.isAppOnDisplay(pkg, displayId); there is no foreground-on-display-0 check and no attempt counter.
