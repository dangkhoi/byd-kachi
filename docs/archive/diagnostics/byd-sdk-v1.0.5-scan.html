BYD AUTO SDK v1.0.5 — what's usable on Mac, and is Windows worth it?

Owner: Đăng Khôi · dangkhoi Date: 2026-08-13 Scanned: <byd-workspace>/sdk (9.7 GB, 50,662 files)
VERDICT: STAY ON MAC — nothing here is Windows-only-and-required
TL;DR
This is not a Windows-only SDK — it is a Windows-packaged copy of the Android SDK (Tools 26 / API 25, ~2018) with BYD's custom bits added. Every valuable part (BYD's compile-time android.hardware.bydauto.* classes, the HTML Javadoc, two PDF guides, a HelloWorld sample) is plain Java/Android and works on macOS as-is. The only Windows-specific files are the redundant Android CLI tools (.exe/.dll/.bat) you already have (newer) on your Mac. Switching to Windows would gain nothing and cost you your working JDK 17 / compileSdk 37 build. Real payoff is unrelated to OS: harvest BYD's android.jar as a compileOnly stub + use the docs to validate/extend the surface ClusterNav reverse-engineered.

3Does the SDK cover what ClusterNav needs?

ClusterNav's BydHal talks to the car entirely by reflection on android.hardware.bydauto.* device classes + a BYDAutoFeatureIds constant table + BYDAutoEventValue. I cross-checked the SDK's shipped classes and Javadoc against that surface:

Key caveat — the SDK is old and partial
SDK v1.0.5 is API 25 / Android 7.1, dated 2018-07-12. Your car runs Android 10 with a newer DiLink ROM. The SDK documents the standard read devices well (speed, tyre, energy, charging, gearbox, …) but it does NOT contain the feature-id/event mechanism ClusterNav actually uses on the ROM, and it does NOT document the hard parts (nav-on-cluster, HUD guide info, ADAS). That's exactly why the project reverse-engineered them — they're newer than / absent from this public SDK. So the SDK validates and enriches ~half of ClusterNav's surface; it does not replace the reverse-engineering for the nav/HUD core.

5Recommendation & next steps (OS-independent)

  1. Stay on macOS. No reason to switch — the working JDK 17 / compileSdk 37 / dadb-OTA setup already ships releases.
  2. Harvest a small BYD stub jar from platforms/android-25/android.jar (just the android/hardware/bydauto/** + android/hardware/BYDAutoManager classes) and add it as compileOnly to :app. That lets you replace reflection with typed calls for the standard devices the SDK covers (speed, tyre, energy, charging, gearbox, instrument units) — safer, autocomplete, no Class.forName. Keep compileOnly: the real classes live on the car; do not bundle them.
  3. Keep reflection for the ROM-only surface — BYDAutoFeatureIds, nav-on-cluster / HUD guide, BYDAutoSpecialDevice, ADAS — the SDK doesn't ship these, so they stay reverse-engineered.
  4. Read the two PDFs + Javadoc as reference to (a) confirm the constants/units ClusterNav already uses and (b) discover unused-but-available devices (radar, panorama, pm2p5, doorlock, light) if future features want them.
  5. Housekeeping: ~4.3 GB is the two redundant zips (sdk_v1.0.5.zip + BYD_AUTO_SDK_v1.0.5.zip) and there's a duplicate extracted copy (byd-auto_sdk_windows vs …_windows 2). You can reclaim ≈6 GB after extracting the one android.jar + DOC&SAMPLE folder. Do not add this 9.7 GB tree to the ClusterNav git repo — keep it as an external reference; commit only a tiny harvested stub jar if you adopt step 2.
Licensing / provenance note
This is a proprietary BYD developer SDK. Treat it as reference + compileOnly stubs; don't redistribute it or commit the full tree publicly. A harvested bydauto-only stub jar (no implementation, API signatures only) is the safe thing to vendor.
