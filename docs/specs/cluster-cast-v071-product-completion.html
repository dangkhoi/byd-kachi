Context

Frozen foundation

  • 0.70 already owns strict parsing and manual BOOTSTRAP → CAST.
  • 409 JVM tests passed at exact-source closure.
  • Stop, unknown-effect and one-compensation fences remain binding.
  • The 0.70 manifest is immutable evidence, not a file to overwrite.

Existing partial surfaces

  • CastAppCatalog has favorites and user-protected preferences, but no icon/default.
  • FloatingBubbleService renders a title and Stop, but uses localized-title policy and no default/favorite menu.
  • RebindReceiver rehydrates and starts the bubble, but V2 auto-cast is absent.
  • Legacy ClusterCast contains old icon/auto-cast code that V2 must not import.

Candidate boundary

  • In: icons, app search/default, protected policy, complete bubble, guarded boot auto-cast.
  • Out: Navigation/HUD changes, legacy mutation reuse, dependency/toolchain upgrades.
  • Off-car only: no APK assemble, install, vehicle command, commit, push or merge.
  • This source-preparation order does not authorize or supersede later exact-build, on-car, provenance, merge or release gates.
  • Every source/test file ≤500 LOC; Activity remains <495.
Safety interpretation: “auto-cast” means a persisted user opt-in handled by the Cast lifecycle owner. It does not mean that a receiver, Activity creation, overlay inflation or localized UI string may emit an opcode. The receiver records intent only; the same manual-intent orchestration performs any later mutation.
Narrow precedence amendment: 0.71 supersedes 0.70 R11’s “lifecycle never starts BOOTSTRAP” only for an origin-tagged BOOT_AUTO request created from post-unlock BOOT_COMPLETED, stored in the existing envelope, atomically claimed by the process-singleton Cast lifecycle coordinator and executed through canonical case 30 plus the existing manual-intent path. Receiver callbacks, LOCKED_BOOT_COMPLETED, package replacement, generic process startup, Activity/Bubble creation and rendering can neither claim nor start BOOTSTRAP. The 0.70 explicit-user pending-placement contract remains unchanged.

D2 — Catalog, default and protection model

Immutable presentation entry

CastAppEntry carries label, package, bounded icon/fallback token, favorite, default and typed protection source. PackageManager work occurs on a catalog worker; Views only bind the result.

  • SYSTEM_PROJECTION locked protected
  • USER_KEEP_SESSION removable only for proven NORMAL
  • UNKNOWN_PROTECTED locked fail-closed; no destructive/Cast action
  • NORMAL ordinary planner policy

Split configuration ownership

The existing AtomicFile envelope owns operational AutomationConfig(revision, defaultPackage, autoCastEnabled, consentVersion), so config change and unclaimed-request supersession are one locked write. Catalog preferences retain only favorites, user-protected normal packages, Bubble opt-in/position and migration marker.

  • default package ≠ pending operation target
  • preselection ≠ dispatch
  • stale default ≠ fallback
  • migration ≠ consent or execution
  • failed write leaves prior model effective

D3 — Canonical Bubble

Bubble refresh uses a bounded worker and lifecycle generation; stale callbacks cannot touch a destroyed overlay. Dragging changes only presentation preferences. Opening or reinflating the Bubble dispatches nothing. Direct Stop never opens Activity to send a second request.

Independent opt-in lifecycle: fresh/absent preference is off. Cast settings and Bubble settings expose the same desired-enabled value. Enable with overlay permission starts only FloatingBubbleService; without permission it renders PERMISSION_REQUIRED guidance and no overlay. An explicit Retry/Start after grant or an allowed presentation rebind may start it, still with zero Cast dispatch. Disable commits false then immediately stops the Bubble service/removes overlay and its notification without requesting Cast Stop. Post-unlock boot and package replacement may restore only an opted-in Bubble; this presentation path is separate from CastAutomationService and cannot record, claim or re-evaluate BOOT_AUTO.

D4 — Durable boot automation state machine

Exact additive envelope schema

AutomationConfig {
  revision: Long >= 0,
  defaultPackage: String?,
  autoCastEnabled: Boolean,
  consentVersion: Int?
}
BootAutomationRequest {
  requestId: UUID, origin: BOOT_AUTO,
  bootId: String, targetPackage: String,
  configRevision: Long, consentVersion: Int,
  state: PENDING | DEFERRED | CLAIMED | COMPLETED | BLOCKED | SUPERSEDED,
  attempt: 0 | 1, reevaluationCount: 0 | 1,
  requestedAtEpochMillis: Long,
  claimedAtEpochMillis: Long?, terminalAtEpochMillis: Long?,
  reason: AutomationReason?
}
AutomationOutcome {
  requestId: UUID, bootId: String, targetPackage: String,
  terminalState: COMPLETED | BLOCKED | SUPERSEDED,
  reason: AutomationReason?, terminalAtEpochMillis: Long
}

AutomationReason is closed: PRIOR_JOURNAL, STOP_REQUESTED, RECOVERY_OR_MANUAL, PROFILE_UNSUPPORTED, TARGET_INVALID, CONFIG_CHANGED, CONSENT_REVOKED, USER_SUPERSEDED, STOP_SUPERSEDED, BOOT_ROLLOVER, FOREGROUND_START_DENIED, NOTIFICATION_PERMISSION_DENIED, NOTIFICATION_START_FAILED, DEADLINE_EXPIRED, CLAIMED_NO_EFFECT_AFTER_RESTART, KNOWN_FAILURE, UNKNOWN_EFFECT, REEVALUATION_EXHAUSTED.

CLAIMED1non-nullnullnull
COMPLETED1non-nullnon-nullnull iff verified success

AutomationOutcome.reason follows the same terminal rule: null if and only if terminalState=COMPLETED; non-null and compatible for BLOCKED/SUPERSEDED. Request invariants are validated on every decode/write: boot equality, the matrix above, package grammar, monotonic revision and outcome compatibility. Any invalid combination is corrupt/unsupported, not a disabled request.

initializeForBoot(observedBootCount) is one store-locked transition. Empty store records the observed ID. Same ID is an idempotent no-op. A different valid ID bumps durable epoch exactly once, updates the envelope boot ID, preserves and marks any unresolved transaction for existing recovery, moves a nonterminal automation request to lastAutomationOutcome(BOOT_ROLLOVER), and only then permits recording the new boot request. It never clears/replays an ISSUED row. Duplicate broadcasts and process restarts with the same ID cannot repeat rollover. Missing/unparseable BOOT_COUNT prevents automation.

Canonical UI v5 adds nullable automationDisposition, automationReason and automationTargetPackage. Presentation precedence is first-match: durable Stop → recovery/manual → active transaction → automation request/outcome → steady stable/cold state. Unknown automation data maps to contract-unmapped manual state, never DISABLED.

Finite permitted triggers

  1. Initial: post-unlock BOOT_COMPLETED durably records/returns one requestId, then requests FGS evaluation. Duplicate/concurrent delivery for the same boot may enqueue only that same still-PENDING ID; service/runtime/claim deduplication prevents a second worker mutation attempt. A record-before-enqueue crash with no redelivery remains unclaimed until next-boot rollover.
  2. Single re-evaluation: only a Cast-owned revalidation alarm for the same request when state is DEFERRED(PRIOR_JOURNAL) and reevaluationCount=0; it increments count before attempting the FGS. Still unresolved, denied or expired becomes terminal BLOCKED.

Activity/Bubble creation, package replacement, generic process startup, periodic refresh, overlay permission change and unrelated alarms are not triggers. User clicking Cast is a new USER intent, never an automation retry.
