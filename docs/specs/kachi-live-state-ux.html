3. Requirements

Chức năng

  • R1 — Kho trạng thái SỐNG (LiveCarState, :core). Một kho giá trị THẬT theo id (nút + datum). Nguồn cập nhật, theo thứ tự ưu tiên:
    (a) sự kiện HAL — listener đăng ký theo feature của các id đang hiển thị;
    (b) đọc lại sau khi ghi — mở rộng R5 (hiện chỉ STEP) sang TOGGLE/SELECT/CYCLE/COVER;
    (c) poll nhịp thấp của bộ lập lịch PERF, chỉ cho id đang hiển thị;
    (d) đọc một lượt khi màn hình hiện lại (onStart).
    AC: nút · chip · widget · voice đều vẽ từ kho này, không đọc thẳng HAL. Giá trị lạc quan chỉ được hiện ở trạng thái “đang gửi” ≤ PENDING_MS (§4.7) rồi nhường cho giá trị thật; lệch ⇒ hiện giá trị thật + ghi 1 dòng log live: <id> muốn=<a> xe=<b>.
  • R2 — Nút nhiều mức (ControlKind.CYCLE). Nhãn hiện đúng mức đang có (“Tắt · Mức 1 · Mức 2 · Mức 3”); tap = mức kế tiếp tính từ mức THẬT (đọc kho R1 trước khi ghi, không phải từ chỉ số RAM); giữ = về mức tắt. Áp cho ghế mát / ghế sưởi (seatID lái mặc định), sưởi vô-lăng nếu có mức, mức lọc… — sinh từ registry, không if (id == "seatc") (CLAUDE.md §7).
    AC: bấm 4 lần trên nút 3 mức phải quay về Tắt; nếu kho chưa có giá trị thật thì nút hiện ⚠ “chưa đọc được trạng thái” và tap bắt đầu từ mức 1 (không giả vờ biết mức hiện tại).
  • R3 — Nút hai chế độ gộp (TOGGLE có stateLabels). “Gió trong / Gió ngoài” là một nút, nhãn hiện chế độ đang có đọc từ getAcCycleMode(), tap = đổi chiều. Cùng khuôn cho: đèn đọc (Tắt/Bật/Theo cửa ⇒ 3 trạng thái ⇒ CYCLE), sấy kính, khoá/mở khoá (chỉ khi có đường ghi — hiện tier=NEEDS_CAR).
    AC: nhãn nút không bao giờ hứa một chế độ mà kho R1 không xác nhận; chưa đọc được ⇒ nhãn trung tính (“Lấy gió”) + ⚠.
  • R4 — Voice dùng CÙNG kho. Câu trả lời đọc số thật (“gió đang mức 3”); “bật ghế mát” ⇒ mức 1; “ghế mát mức 2” ⇒ đặt thẳng mức 2. AC: không còn đường nào trong VoiceDispatcher dựng câu từ con số vừa gửi khi kho có giá trị thật.
  • R5 — Thành thật khi không đọc được. HAL không có sự kiện/getter cho một id ⇒ nút ghi rõ “chưa đọc được trạng thái” (không đoán, không hiện số lạc quan quá PENDING_MS), và catalog khả năng gắn status ⚠ cho mã đó.
  • R6 — Không thêm tải. Listener đăng ký/huỷ theo tập id đang hiển thị + vòng đời màn (onStart/onStop). Số lệnh HAL/phút sau thay đổi ≤ ngân sách của spec PERF, đo bằng KachiPerf.dueLine.

Phi chức năng

  • R-nf1 — Thuần & test off-device. LiveCarState + luật CYCLE + map eventType→id nằm ở :core, không import Android ⇒ test JVM. Phần chạm framework (Proxy listener) ở :app, mỏng nhất có thể.
  • R-nf2 — Degrade-safe. Off-car / máy ảo: không có device ⇒ không đăng ký được ⇒ kho rỗng ⇒ UI “—” / ⚠, không crash, không ném ra ngoài (cùng lệ BydHalGateway).
  • R-nf3 — Tương thích lưu trữ. KHÔNG đổi định dạng prefs/SlotCodec: DockConfig.enabled vẫn là danh sách mã trần; CYCLE là kiểu trong registry, không phải một trường lưu mới. Cấu hình người dùng đã lưu đọc lên nguyên vẹn.
  • R-nf4 — An toàn luồng. Sự kiện HAL tới trên luồng binder; UI đọc trên luồng chính ⇒ kho phải an toàn đa luồng (StateFlow + update nguyên tử, đúng khuôn CarStatusRepository.kt:57).

4.2 Kho LiveCarState (:core)

// core/src/main/kotlin/com/byd/clusternav/launcher/LiveCarState.kt

    fun put(id: String, value: Int?, src: LiveSrc) { … }

    fun markPending(id: String, wanted: Int) { … }

    /** Giá trị để VẼ: đang-gửi còn hạn ⇒ wanted; ngược lại ⇒ giá trị thật; chưa có ⇒ null (⚠). */
    fun shown(id: String): Int? = …

    /** true khi đang trong cửa sổ "đang gửi" (ô vẽ mờ + chấm nhịp). */
    fun isPending(id: String): Boolean = …

Vì sao value: Int? chứ không phải Int mặc định 0: đúng bài học đã ghi ở HalBindingTable.readRaw (ĐO HalBindingTable.kt:34-35) — một con số vô nghĩa hiện lên ô còn tệ hơn một dấu “—”, vì người lái tin nó. null = “chưa đọc được”, và UI phải nói đúng chữ đó (R5).

Vì sao không nhét vào CarStatus đang có: CarStatus là bản ghi phẳng có tên trường cho datum ĐỌC, còn kho này phải tra theo mã chuỗi (mọi nút + mọi datum, sinh từ registry). Nhét vào nhau thì mỗi nút mới lại phải thêm một trường — đúng kiểu case-by-case mà CLAUDE.md §7 cấm. Hai lớp sống cạnh nhau; CarDataAdapter ghi vào cả hai trong cùng một lượt đọc (không đọc hai lần).

4.3 Khoá ĐỌC riêng cho nút — ControlDef.readKey

Gốc bệnh ở §2.2 (đọc bằng khoá GHI) được chữa bằng một trường dữ liệu, không phải một nhánh rẽ theo tên:

data class ControlDef(
    …,
    /** Mã DATUM đọc trạng thái thật của nút này (trỏ vào TelemetryRegistry). "" ⇒ chưa có đường đọc ⇒ ⚠. */
    val readKey: String = "",
    /** Tham số của getter khi cần (seatID ghế, area kính/sấy). null ⇒ getter 0-arg. */
    val readArg: Int? = null,
)

Phần lớn đường đọc đã tồn tại trong TelemetryRegistry (ĐO): fan → ac_wind (TelemetryRegistry.kt:248), temp → inside_temp (:242), recirc → ac_cycle (:250), win_lf → window_lf (:274). Mã nào chưa có datum thì thêm datum (một dòng t(...)), để getter của xe chỉ được khai một chỗ duy nhất trong cả dự án — không mọc một bảng getter thứ hai cho nút.

4.4 Nghe sự kiện HAL — BydHalEvents (:app, java.lang.reflect.Proxy)

LiveCarState:core · thuần
HalEventMap:core · eventType → id · thuần, test được
BydHalEvents:app · Proxy cài IBYDAutoListener · đăng ký/huỷ theo màn
BydHal / BydFeatureIds:app · reflection SẴN CÓ, không mở đường mới
AbsBYDAutoDevice.registerListener(l, int[] featureIDs)framework xe · qua checkDeviceFeatures → enableDevice

Vì sao Proxy: android.hardware.IBYDAutoListener nằm trong framework.jar của xe, không có trong SDK ⇒ không implements được lúc biên dịch. Interface chỉ có 3 method (ĐO IBYDAutoListener.java:6-12) nên Proxy.newProxyInstance là đường sạch, cùng họ reflection mà BydHal đang dùng:

// :app — BydHalEvents.kt (rút gọn)
val iface = Class.forName("android.hardware.IBYDAutoListener")
val listener = java.lang.reflect.Proxy.newProxyInstance(iface.classLoader, arrayOf(iface)) { _, m, args ->
    when (m.name) {
        "onDataChanged" -> {                       // args[0] : IBYDAutoEvent
            val ev = args!![0]
            val type = ev.javaClass.getMethod("getEventType").invoke(ev) as Int
            val value = ev.javaClass.getMethod("getValue").invoke(ev) as Int
            onEvent(type, value)                    // → HalEventMap → LiveCarState.put(..., EVENT)
        }
        "onError" -> KachiLog.w("hal event lỗi: ${args?.getOrNull(1)}")
        else -> Unit                                // onDataEventChanged: chưa dùng
    }
    null
}
device.javaClass.getMethod("registerListener", iface, IntArray::class.java)
      .invoke(device, listener, readFeatureIds)     // id ĐỌC, KHÔNG phải id _SET

4.6 Kiểu mới ControlKind.CYCLE — và vì sao không mở rộng SELECT

enum class ControlKind { TOGGLE, STEP, COVER, SELECT, BUTTON, CYCLE }   // CYCLE nối CUỐI ⇒ ordinal cũ không đổi

/** Một mức của nút CYCLE: nhãn + giá trị GHI xuống xe + (các) giá trị ĐỌC khớp mức này. */
data class CycleState(
    val label: String,          // "Tắt" · "Mức 1" · "Mức 2"
    val labelEn: String,
    val write: Int,            // ví dụ ghế mát: OFF=1 · LOW=2 · HIGH=3  ([ĐO] BYDAutoSettingDevice.java:326-332)
    val read: Set<Int> = setOf(write),   // đọc có thể trả nhiều mã cho cùng một mức
)
  • Tap = CycleLogic.next(states, current) với current lấy từ kho R1; kho chưa có ⇒ bắt đầu từ mức 1 và nút mang ⚠ (R2 AC).
  • Giữ = về states[0] (mức tắt). Một cử chỉ duy nhất để thoát, không phải bấm vòng 3 lần.
  • Vì sao không dùng SELECT có tap-xoay-vòng: SELECT là “bày ra danh sách rồi chọn” (ambient_color 5 màu — xoay vòng qua 5 màu là UX tệ), còn CYCLE có khái niệm mức tắt ở chỉ số 0 và luật giữ-để-tắt. Hai luật khác nhau ⇒ hai kiểu; nhét chung thì mỗi chỗ vẽ lại phải hỏi “SELECT này là loại xoay hay loại bày?” — đúng kiểu cờ-trong-cờ đã sinh ra lỗi ở ControlTileState.
  • Sinh từ registry: ControlTileFactory.actionTile (ĐO ControlTileFactory.kt:56) thêm đúng một nhánh CYCLE -> tileCycle(def, …), không có chỗ nào so tên mã.
