  • AC5 (option B, recommended) — App opens with the master switch OFF by default; no adb/dadb runs at startup. The grant + connect fire only when the user turns the switch ON, reducing dadb contention.

4Design

T1 — Reuse the proven dadb self-grant

Root cause (verified by source read)

In MainActivity the button branches on permission:

if (notificationAccessGranted()) {
    NavConnect.reconnect(applicationContext)     // ← dadb allow_listener path (works)
} else {
    promptNotificationAccess()                   // ← opens Settings screens (dead end on IVI)
}

promptNotificationAccess() → openNotificationAccessSettings() tries ACTION_NOTIFICATION_LISTENER_DETAIL_SETTINGS (API 30+, skipped on API 29), ACTION_NOTIFICATION_LISTENER_SETTINGS, then ACTION_APPLICATION_DETAILS_SETTINGS. The locked DiLink IVI does not expose those activities, so the BYD system shows “Hệ thống IVI không hỗ trợ hoạt động này” (confirmed not an app string via grep). The grant that actually works — cmd notification allow_listener over dadb uid-shell — already exists in NavConnect.doReconnect, but is only reachable from the already-granted branch.

Change set

  • New NavConnect.selfGrant(ctx): single-flight, background — cmd notification allow_listener $COMP then NotificationListenerService.requestRebind(...), then poll NavNotificationListener.connected. No disallow for a first grant (disallow→allow only when already listed). Reuses LocalDeviceShell.session / AdbKeys exactly like doReconnect.
  • MainActivity missing-permission branch → call selfGrant with a “Đang cấp quyền…” toast; on failure, surface the “bấm Allow USB debugging trên xe” hint and only then offer the Settings dialog fallback.
  • Option B RECOMMENDED — flip Prefs.enabled default to false; gate startup NavConnect.ensureConnected() behind enabled; run selfGrant + connect when the master switch is turned ON. Once granted, the permission persists across reboots (RebindReceiver re-binds), so steady-state launches touch no adb.
  • Cleanup — fix the stray comment artifact in doReconnect (…client dadb khác)selfGrant)).
Recommendation
Do both: the selfGrant core fix (this is the actual bug) and Option B (default-OFF startup) to cut dadb contention as you asked. Both are small and independent. If you prefer the minimum, the selfGrant fix alone closes AC1–AC4.

Tech validation: no new library. The grant verb (cmd notification allow_listener), the dadb loopback, and requestRebind are all already proven in this repo. Nothing to Context7.

T3 — Accessibility key capture → assistant intent

No-root pattern (as used by BYD Binti): capture the hardware key in an AccessibilityService that requests key filtering, then fire an intent to the chosen assistant. This app already has NavAccessibilityService, so no new service or permission is needed — only an onKeyEvent override plus two flags in its config.

Refined scope (approved 2026-08-13) — configurable, no native override

  • Configurable: user picks button (candidate keycodes — VOICE_ASSIST 231, ASSIST 219, media/steering — or “learn key” to capture the real code on-car) + gesture (nhấn / nhấn-giữ) + target. Stored in Prefs; the pure decision lives in VoiceKeyMatcher (:core, JVM-tested).
  • No native override: onKeyEvent returns true (consume) only for the exact configured combo. PRESS consumes the chosen key’s DOWN+UP; HOLD lets a short tap pass through (native intact) and consumes only the long-press. Every other key/gesture → super.onKeyEvent. Feature OFF ⇒ always pass-through.
  • Enablement: the feature needs the accessibility service on. Turning the switch ON self-enables it over dadb (NavConnect.grantAccessibility appends enabled_accessibility_services), same “ADB permission” pattern as T1 — no dead Settings screen.
  • Keymap: reuse known Android candidates (no on-car re-probe); “learn key” is the fallback if the button’s code differs on this trim (“lên xe test không OK thì mới mò”).

Launch targets (user-selectable)

  • Google Assistant / Gemini — Intent(Intent.ACTION_VOICE_COMMAND) / ACTION_ASSIST, fallback to launching the assistant package.
  • BYD voice “小迪” — com.byd.autovoice (present in firmware; exact launch intent to confirm on-car).
  • Generic — RecognizerIntent.ACTION_VOICE_SEARCH_HANDS_FREE.
Context7 verification
Verified against /websites/developer_android: the android.service.voice VoiceInteraction framework and Assistant Built-in Intents / App Actions exist at API 29 (the car’s level). AccessibilityService.onKeyEvent + canRequestFilterKeyEvents is stable since API 18. Unverified until on-car: which client-launch intent the installed assistant actually answers, and whether the hardware key reaches accessibility (vs system-consumed) — hence the “learn key” capture mode.
