4Design

Root cause of J1 — two emission paths, only one has a heartbeat

Navigation drives the cluster through two independent paths. Only the cluster-lane path has a heartbeat; the HAL path (which feeds the windshield HUD + the "Giữa+ETA" centre) has none, so it goes stale on straights and the OEM blanks it.

The windshield HUD reads its arrow from INSTRUMENT_GUIDE_INFO_SIMPLE_SET, written by BydHal.writeNavFrame — reached only through NavigationHudOwner (System B). ClusterBroadcaster.emitHud is a T7 no-op (zero physical writes). So the flicker is entirely a System-B staleness problem.

J1 — keep-alive inside NavigationHudOwner off-car fix

  • Pure policy (core): new HudKeepAlivePolicy(intervalMs = 400) — onFrameWritten(now) / onCleared() / shouldReassert(now) = hasFrame && now − lastWrite ≥ interval. No Android deps → JVM-testable. Clock is injected (monotonic elapsedRealtime).
  • Owner wiring (app): NavigationHudOwner gets a single daemon ScheduledExecutorService started in start() (idempotent), ticking at the policy interval. The delivery lambda calls onFrameWritten after a successful HAL write and onCleared on any clear (incl. mode OFF). On tick, if shouldReassert, resubmitApplied() submits the last applied (icon, seg, road) directly to the worker — bypassing push()'s dedup. stop()/close() cancel the task; close() shuts the scheduler down.
  • Why re-assert (not re-project): J1 is purely "don't blank". Re-asserting the last raw value keeps the element alive without changing distance behaviour. Dedup-suppressed pushes do not reset the keep-alive clock, so a stale display is always refreshed within one interval.
  • Boundary: lane vs HUD are both the Navigation track — this does not touch the Nav↔Cast two-track rule. The keep-alive is contained in the owner; ClusterBroadcaster keeps zero reference to it (asserted by PhysicalHudOwnershipTest + a new wiring assertion).
On-car verify
The exact OEM staleness window is a vehicle behaviour. Start at 400 ms (matches the proven cluster-lane cadence, comfortably under the observed ~1s blank); tune if needed. Also confirm re-writing status=2 + screen-mode every 400 ms while parked does not fight the OEM.

J2 — screen-read ground-truth column + offline analysis off-car fix

The comparison log already exists: NavDistanceLog writes a CSV per frame with rawGmaps_m (notification), projected_m (interp), display_m (quantized), plus closing_mps / speed_mps. What was missing is the on-screen GMaps distance (the smooth number the accessibility reader sees), which is the real ground truth. Changes:

  • Interpolator (core): TurnDistanceInterpolator.refine(seg, now) already receives the accessibility reading; record it as lastRefineSeg/lastRefineAt (even when there is no baseline yet) and expose lastRefined() / lastRefinedAt(). Cleared in reset().
  • Log (app): NavDistanceLog header + record(...) gain screenRead_m and screenRead_age_ms (age from elapsedRealtime − lastRefinedAt, or -1 when never read). New header: t_ms,rawGmaps_m,projected_m,display_m,closing_mps,speed_mps,screenRead_m,screenRead_age_ms,road,key.
  • Wiring (app): ClusterBroadcaster.sendFrame reads TurnDistanceInterpolator.lastRefined()/lastRefinedAt() (same place it already reads closingRate()) and passes them to record. No new dependency, no HAL reference — PhysicalHudOwnershipTest stays green.
  • Analysis (script): scripts/analyze-nav-distance-log.py (Python 3, stdlib only). Reads columns by header name (robust to the added columns; also reads old 8-col logs). For rows with a fresh screen-read (age ≥ 0 and ≤ 1500 ms) it reports mean / RMS / p50 / p95 / max of projected − screenRead, display − screenRead, and rawGmaps − screenRead (notification lag). It also counts display "jumps" (|Δdisplay| over a threshold while moving) and prints a tuning summary pointing at the knobs below.

Concurrency (top priority) — no deadlock, no lost heartbeat

  • Lock ordering: every method acquires at most one of {dedupLock, keepAliveLock, HudKeepAlivePolicy lock} at a time and releases before taking the next — in the delivery lambda synchronized(dedupLock){…} closes before keepAlive.onFrameWritten/onCleared, and keepAliveTick reads the policy then resubmitApplied() takes dedupLock then releases before worker.submit. dedupLock and the policy lock are never held simultaneously by any thread → no cross-lock cycle. The only nesting is keepAliveLock → scheduler-internal in start/stop/close, which has no reverse path.
  • Task survival: keepAliveTick body wrapped in runCatching{…}.onFailure{log} → a thrown tick cannot kill scheduleWithFixedDelay.
  • Idempotent start: worker.setEnabled(true) is idempotent and the if (keepAliveTask == null) guard under keepAliveLock prevents a second task — safe from both createCoordinator and setOutputEnabled(CLUSTER_LANE,true).
  • Lifecycle: stop() cancels the task (cancel(false), no mid-write interrupt) + onCleared(); close() cancels + shutdownNow(). Disabled worker submit() returns DISABLED (safe no-op).
  • Clock integrity: a dedup-suppressed push() returns early without submitting → delivery lambda never runs → onFrameWritten not called → keep-alive clock is not reset, so a stale display is always refreshed within one interval. onFrameWritten fires only after a real writeNavFrame; the OFF/clear branches call onCleared and reset applied state, disengaging keep-alive.
  • Sequence: AtomicLong.getAndIncrement() feeds guidanceFrame()/clearFrame() across push()/reapply()/resubmitApplied()/stop() from both the coordinator and scheduler threads — atomic, no torn reads.
